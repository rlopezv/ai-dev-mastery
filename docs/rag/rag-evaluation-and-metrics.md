## 1. Intuition

A RAG pipeline can fail in two distinct places: it can retrieve the wrong documents, or it can retrieve the right documents but generate the wrong answer. These are different failure modes with different causes and different fixes. Evaluating the pipeline as a black box — "did the user get a correct answer?" — conflates both and makes debugging impossible.

RAG evaluation separates the measurement into two stages: does the retrieval step return the content that contains the answer, and does the generation step produce an answer that is grounded in and consistent with that content?

---

## 2. Explanation

### 2.1 Why

Improving a RAG pipeline without measurement is guesswork. Changing chunk size, embedding model, or context ordering each affects pipeline quality in different ways — but without metrics, the effect of a change is invisible. A retrieval precision measurement tells you whether a change to chunking improved the quality of what the model receives. A faithfulness measurement tells you whether the model is using that content correctly.

Without evaluation, teams routinely fix the wrong component: improving prompts when retrieval is broken, or tuning chunk size when the model is ignoring the context.

### 2.2 How

**Evaluation dataset** — the foundation of any RAG evaluation. An evaluation dataset consists of (query, expected_chunks, expected_answer) triples. The `expected_chunks` field identifies which chunks in the index contain the information needed to answer the query. The `expected_answer` is the correct answer against which generated outputs are compared.

Building an evaluation dataset requires effort: queries and ground truth must be written by a human or generated by an LLM and validated. For early-stage pipelines, 50–100 diverse questions drawn from the corpus are sufficient to detect major deficiencies.

**Retrieval metrics** measure the quality of the retrieval step independently:

- **Precision@k** — of the k chunks retrieved, what fraction contain information relevant to the query:
  ```
  Precision@k = |relevant ∩ retrieved| / k
  ```
- **Recall@k** — of all relevant chunks in the index, what fraction were retrieved in the top k:
  ```
  Recall@k = |relevant ∩ retrieved| / |relevant|
  ```
- **MRR (Mean Reciprocal Rank)** — the mean of the reciprocal of the rank at which the first relevant chunk appears:
  ```
  MRR = (1/|Q|) Σ 1/rank_i
  ```
  MRR rewards pipelines that surface the correct chunk near the top of the list rather than anywhere in top-k.

**Generation metrics** measure the quality of the generated answer given the retrieved context:

- **Faithfulness** — whether the generated answer is grounded in the retrieved context, without introducing claims not supported by the provided text. Measured by LLM-as-judge: a grader model is given the context and the answer and asked whether every claim in the answer can be traced to the context.
- **Answer relevance** — whether the generated answer actually addresses the question. A long, grounded but off-topic answer scores low on relevance. Measured by LLM-as-judge or by embedding similarity between the question and the answer.
- **Context utilization** — what fraction of the relevant content in the assembled context was used in the answer. Low utilization indicates the model is ignoring retrieved content (possibly falling back to parametric memory).

**LLM-as-judge** is the practical evaluation approach for semantic quality metrics. A separate LLM call evaluates the output against a rubric, returning a binary or scalar score. This replaces expensive human annotation for high-frequency evaluation but requires a grader prompt that has been validated against a human-labeled reference set to detect systematic bias.

### 2.3 Code example

```python
# See: labs/rag/lab-rag-evaluation/main.py
# Retrieval precision and recall for a fixed evaluation set

def evaluate_retrieval(pipeline, eval_set: list[dict],
                       top_k: int = 5) -> dict:
    """
    eval_set: list of {"query": str, "relevant_chunk_ids": list[str]}
    Returns avg Precision@k and Recall@k.
    """
    precisions, recalls = [], []
    for item in eval_set:
        retrieved = pipeline.retrieve(item["query"], top_k=top_k)
        retrieved_ids = {c["id"] for c in retrieved}
        relevant_ids  = set(item["relevant_chunk_ids"])

        tp = len(relevant_ids & retrieved_ids)
        precisions.append(tp / top_k)
        recalls.append(tp / len(relevant_ids) if relevant_ids else 0.0)

    return {
        "precision_at_k": sum(precisions) / len(precisions),
        "recall_at_k":    sum(recalls)    / len(recalls),
    }
```

## 3. Table

| Metric | Measures | Stage | Typical target |
|--------|---------|-------|----------------|
| Precision@k | Fraction of retrieved chunks that are relevant | Retrieval | ≥ 0.7 |
| Recall@k | Fraction of relevant chunks that are retrieved | Retrieval | ≥ 0.8 |
| MRR | Rank position of first relevant chunk | Retrieval | ≥ 0.75 |
| Faithfulness | Answer grounded in context, no fabricated claims | Generation | ≥ 0.85 |
| Answer relevance | Answer addresses the question | Generation | ≥ 0.80 |
| Context utilization | Fraction of relevant context used in answer | Generation | ≥ 0.60 |

| Failure pattern | Affected metric | Likely cause | Fix |
|----------------|----------------|-------------|-----|
| Correct answer not in context | Recall@k low | Chunking too coarse, top-k too small | Smaller chunks, larger top-k |
| Irrelevant chunks dominate | Precision@k low | Embedding model weak, no reranking | Better model, add reranking |
| Answer adds ungrounded claims | Faithfulness low | Model uses parametric memory | Stronger "answer from context only" instruction |
| Answer doesn't address question | Relevance low | Model distracted by context | Clearer query framing, shorter context |

## 4. Engineering Implications

**Evaluation datasets must be static.** Comparing two pipeline configurations requires that both run against exactly the same queries and ground truth. A changing evaluation set makes results incomparable. Treat the evaluation dataset as a versioned artifact.

**LLM-as-judge is a model, not ground truth.** A grader LLM can disagree with a human rater on borderline cases. Validate the grader against a human-labeled sample of 30–50 examples before trusting its scores at scale. If the grader agrees with humans on 90%+ of examples, it is reliable enough for pipeline development.

**Retrieval and generation metrics must both be measured.** A pipeline with perfect generation faithfulness but low retrieval recall only succeeds when the correct information happens to be retrieved. A pipeline with high retrieval recall but low faithfulness is retrieving correctly but hallucinating in the generation step. Both stages must be healthy for the pipeline to be reliable.

**Metric targets depend on use case.** A customer support bot can tolerate Precision@5 of 0.7; a medical information assistant cannot. Define target thresholds before evaluation, not after observing the scores.

## 6. Failure Modes and Limitations

**Evaluation set coverage bias.** If the evaluation queries are all of the same type (e.g., factual lookups), metrics may be high for that query type but fail to detect problems with multi-hop reasoning queries or ambiguous queries. Build evaluation sets that cover the full range of query types expected in production.

**Recall is hard to measure without exhaustive relevance labels.** Computing Recall@k requires knowing all relevant chunks in the index — which requires labeling every chunk for every query. In practice, approximate recall is computed by labeling only the top-k results from a high-recall baseline. This underestimates true recall.

**LLM-as-judge grader drift.** The grader model's behavior changes when the model version is updated. A score of 0.87 faithfulness from GPT-4-turbo and GPT-4o may reflect a different grading standard, not a real quality change. Pin the grader model version when using LLM-as-judge.

**Faithfulness conflates citation with accuracy.** A model can faithfully reproduce incorrect information from a poor chunk — it is technically faithful (consistent with context) but factually wrong. Faithfulness measures groundedness, not correctness. For accuracy, ground truth answers are needed.

---

## 7. Summary

RAG evaluation measures the pipeline at two independent stages. Retrieval metrics — Precision@k, Recall@k, MRR — measure whether the correct content reaches the context. Generation metrics — faithfulness and answer relevance — measure whether the model uses that content correctly. LLM-as-judge enables semantic evaluation at scale without full human annotation. A static evaluation dataset is the prerequisite for comparing pipeline configurations meaningfully.
