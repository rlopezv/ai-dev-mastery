# LLM Fundamentals — Implementation Reference

## Navigation

## 1. Implementation Overview

The inference pipeline described in `architecture.md` is implemented across two tools: the Ollama HTTP API, which wraps the transformer and sampling stages, and `tiktoken`, which exposes the tokenizer as a standalone library. Each pipeline component maps to a concrete interface that the labs make observable.

> **Note:** This document contains orientative code — structures, interfaces, and representative snippets.
> It is not directly executable. For complete, runnable implementations see the labs
> referenced in `implementation_refs`.

| Pipeline component | Tool | Interface |
|--------------------|------|-----------|
| Tokenizer | `tiktoken` | `Encoding.encode()` / `Encoding.decode()` |
| Context assembler | Application code | String formatting + token count validation |
| Transformer + autoregressive loop | Ollama API | `POST /api/generate` |
| Sampling algorithm | Ollama API | `options` block in the request body |

---

## 2. Core Patterns

| Pattern | What it implements | When to apply |
|---------|-------------------|---------------|
| `generate` | Single forward pass + autoregressive loop until stop condition | Any time a text completion is needed |
| `tokenize-and-count` | Tokenizer encode before sending | Before any request where context budget matters |
| `stream-generate` | Autoregressive loop with token-by-token delivery | Interactive output, long responses |
| `parameter-sweep` | Same prompt, varied `options` block | Calibrating sampling behavior for a task |
| `context-fill` | Progressively growing input to approach the budget boundary | Testing truncation behavior and limit enforcement |

---

## 3. Component Mapping

| Architecture component | Implementation |
|------------------------|----------------|
| Tokenizer (encode) | `tiktoken.get_encoding(name).encode(text) → list[int]` |
| Tokenizer (decode) | `tiktoken.get_encoding(name).decode(ids) → str` |
| Context assembler | Concatenate system + history + user strings; validate `len(encode(prompt)) + max_output ≤ limit` |
| Transformer + autoregressive loop | `POST /api/generate` with `stream: false`; loop is internal to Ollama |
| Sampling algorithm | `options.temperature`, `options.top_k`, `options.top_p` |
| Stop condition | `options.num_predict` (token budget) or `options.stop` (token sequences) |
| Pipeline telemetry | `prompt_eval_count` (input tokens), `eval_count` (output tokens), `total_duration` (ns) |

## 4. Data Structures and Interfaces

**Generate request — full structure:**

```python
# Orientative — see labs/llm-fundamentals/lab-llm-anatomy/main.py
{
    "model": str,           # model identifier as registered in Ollama
    "prompt": str,          # assembled context: system + history + user
    "stream": bool,         # False → complete response; True → token stream
    "options": {
        "temperature": float,    # 0.0–2.0; scales logit distribution
        "top_k": int,            # 1–100+; restricts candidate pool by count
        "top_p": float,          # 0.0–1.0; restricts by cumulative probability
        "num_predict": int,      # max completion tokens; always set explicitly
        "stop": list,            # optional stop sequences
    }
}
```

**Generate response — relevant fields:**

```python
# Orientative — see labs/llm-fundamentals/lab-llm-anatomy/main.py
{
    "response": str,             # generated text
    "done": bool,                # True when autoregressive loop has terminated
    "prompt_eval_count": int,    # tokens consumed from input (includes framing)
    "eval_count": int,           # tokens generated by the loop
    "total_duration": int,       # wall-clock time in nanoseconds
}
```

**Context budget check:**

```python
# Orientative — see labs/llm-fundamentals/lab-context-window/main.py
def fits_in_context(
    prompt: str,
    max_output: int,
    context_limit: int,
    enc: tiktoken.Encoding,
) -> tuple:
    input_tokens = len(enc.encode(prompt))
    fits = (input_tokens + max_output) <= context_limit
    return fits, input_tokens
```

**Parameter sweep:**

```python
# Orientative — see labs/llm-fundamentals/lab-inference-parameters/main.py
def sweep(prompt: str, configs: list) -> None:
    for cfg in configs:
        result = generate(prompt, **cfg)
        print(cfg, "→", result["response"][:80])
```

## 5. Design Decisions

**Why tiktoken for token counting instead of the Ollama `/api/tokenize` endpoint.**
tiktoken runs in-process with no network call, making it the right tool for budget validation *before* sending a request. The Ollama endpoint is accurate for the specific model's tokenizer but introduces a round-trip. For the labs' purpose — learning that token counts must be computed explicitly — the in-process approach makes the mechanics more transparent.

**Why `stream: false` in the labs.**
Streaming is the correct production default for interactive applications, but it splits the response across many JSON lines and makes metadata fields harder to inspect. Using `stream: false` returns a single JSON object with all telemetry fields populated, which is better for observation. The `stream-generate` pattern exists for completeness but is not used in the observation labs.

**Why the context assembler is application code, not a library.**
There is no standard library for context assembly — it is always application-specific. Different applications assemble context differently: RAG injects retrieved chunks, agents inject tool results, multi-turn chat injects conversation history. The pattern in section 2 represents the minimal assembly logic; the `memory-context` module covers more sophisticated strategies.

**Why `num_predict` must always be set explicitly.**
Without a cap, the autoregressive loop runs until a stop token is generated. For some prompts and models, that stop token may never appear within a reasonable token budget, producing an arbitrarily long response. Setting `num_predict` is not a creative constraint — it is a cost and context control that every production caller must apply.

## 8. Trade-offs and Constraints

**`prompt_eval_count` includes model framing overhead.** Ollama wraps the raw prompt in a chat template before tokenizing (e.g., `[INST]...[/INST]` for Llama models). The reported `prompt_eval_count` will be higher than a raw tiktoken count of the same string. This delta is typically 5–15 tokens and is predictable for a given model — budget calculations should add a small margin.

**tiktoken is not accurate for non-OpenAI models.** The `cl100k_base` schema matches GPT-4's tokenizer. Llama3 uses a SentencePiece-based tokenizer with a different vocabulary. Token counts will differ by 0–20% depending on content. For tight budget calculations on Llama models, use `/api/tokenize` in Ollama. The labs use tiktoken for its standalone usability and pedagogical clarity.

**The context assembler owns truncation decisions.** The model does not signal when content was dropped — the application must track token counts and decide what to cut. Strategies (drop oldest, summarize, compress) are application-level choices with different quality trade-offs. This is the central problem of the `memory-context` module.

**Sampling parameters interact non-linearly.** Setting temperature, top_k, and top_p simultaneously can produce unexpected distributions. High temperature widens the distribution; low top_p immediately re-narrows it; these two controls can partially cancel each other. Calibrate one parameter at a time before combining them.

---

## 9. Failure Modes

**Using character or word count as a token budget proxy.** Non-English content, code, numbers, and URLs tokenize at significantly different rates than English prose. A prompt that appears to fit based on word count may overflow the context window when tokenized. Always count tokens explicitly.

**Assuming `temperature=0` output is stable across model updates.** Greedy decoding is deterministic for fixed weights. When Ollama updates a model or when a different quantization is used, the output changes even at temperature=0. Temperature=0 guarantees reproducibility within a session, not across deployments.

**Letting output tokens consume the majority of the context budget.** When `num_predict` is large and the input is already long, the generated response may fill the remaining window, leaving no room in subsequent turns. In multi-turn applications, the sum of input tokens and expected output tokens must be planned against the full context limit, not just the current turn.

**Conflating the tokenizer schema with the model.** A tiktoken encoding name (`cl100k_base`) is a tokenizer schema, not a model identifier. The same schema is shared across GPT-3.5, GPT-4, and embedding models. Using the wrong schema produces incorrect token counts. Match the schema to the model family, not to the application's preferred counting library.

---

## 10. Summary

The inference pipeline maps cleanly to two tools: tiktoken for the tokenizer stage, and the Ollama `POST /api/generate` endpoint for the transformer and sampling stages. The five patterns — `generate`, `tokenize-and-count`, `stream-generate`, `parameter-sweep`, `context-fill` — cover the full observable surface of the pipeline. The key design constraints are the framing overhead in `prompt_eval_count`, the tokenizer schema mismatch between tiktoken and Llama3, and the application's sole responsibility for context budget management.
