## 1. Intuition

The context window is the model's working memory. Every token the model can see during a single generation — system instructions, conversation history, retrieved documents, and the response being built — must fit within a fixed token limit. Nothing outside that limit exists for the model in that call.

A useful analogy: it is a fixed-size RAM buffer. The processor (model) can only operate on what is currently in RAM (context window). Content that does not fit is not paged in — it is simply unavailable, with no error and no notification.

---

## 2. Explanation

### 2.1 Why

The context window limit is a direct consequence of self-attention scaling. As established in `llm-architecture.md`, every token attends to every other token in a single forward pass. Processing n tokens requires O(n²) attention operations in memory and compute. Doubling the context length quadruples the attention cost. At 128k tokens, the attention matrix alone is too large to fit naively in GPU memory without architectural optimizations.

Model families have extended context windows progressively — GPT-3 at 4k, GPT-4 Turbo at 128k, Gemini 1.5 at 1M — through techniques such as sparse attention and ring attention. These reduce the constant factor but do not change the fundamental quadratic relationship. A fixed limit remains in every production model.

### 2.2 How

Every token processed in a single API call consumes from the same budget:

**1. System prompt tokens** — Instructions provided before the conversation begins. These tokens are present in every request and are charged every time.

**2. Conversation history tokens** — Prior turns included to give the model context. As a conversation grows, history accumulates and eventually must be truncated or summarized.

**3. Retrieved content tokens** — Documents, tool results, or file contents injected by the application layer (RAG, function call results). These can be large and variable.

**4. User message tokens** — The current input turn.

**5. Completion tokens** — Tokens generated by the model in response. These are bounded by `max_tokens` set by the caller and are generated one token at a time, each consuming one slot in the remaining budget.

The constraint is:

```
input_tokens + completion_tokens ≤ context_window_limit
```

When input tokens alone approach the limit, the application must intervene — truncating history, summarizing content, or reducing retrieved chunks. The model does not signal when content was dropped; it silently works with whatever fits.

### 2.3 Code example

```python
# See: labs/llm-fundamentals/lab-context-window/main.py
import tiktoken

enc = tiktoken.get_encoding("cl100k_base")

system_prompt = "You are a helpful assistant."
user_message = "Summarize the following document:\n\n" + document_text

input_tokens = (
    len(enc.encode(system_prompt)) +
    len(enc.encode(user_message))
)

context_limit = 8192
max_output_tokens = 512

remaining = context_limit - input_tokens
if remaining < max_output_tokens:
    print(f"Insufficient space: only {remaining} tokens remain for output.")
else:
    print(f"Input: {input_tokens} tokens. Output budget: {remaining} tokens.")
```

## 3. Context Consumption by Use Case

| Use case | Typical input tokens | Typical output tokens | Constraint level |
|----------|---------------------|----------------------|-----------------|
| Single Q&A | 50–200 | 100–500 | None |
| Multi-turn chat (10 turns) | 1,000–5,000 | 200–500 | Monitor history growth |
| Document summarization | 2,000–50,000 | 200–1,000 | May require chunking |
| RAG with 5 retrieved chunks | 3,000–15,000 | 300–800 | Budget retrieval carefully |
| Code review (large file) | 5,000–30,000 | 500–2,000 | May require file splitting |
| Full codebase analysis | 100,000+ | 1,000–5,000 | Requires large-context model |

## 4. Engineering Implications

**Context window size does not equal retrieval quality.** Research on long-context models shows that attention is not uniform across the full window. Content positioned in the middle of a very long context receives less reliable attention than content at the beginning or end — the "lost in the middle" effect. A 128k context window does not guarantee equal fidelity across all 128k tokens.

**Input tokens cost money on every call.** API pricing charges per input token per request. A 500-token system prompt costs money on every single API call regardless of how short the user message is. System prompt length is an operating cost, not a one-time cost.

**Conversation state management is the application's responsibility.** The model has no memory between calls. The application must decide what history to include, when to truncate, and when to summarize. There is no built-in mechanism — this is the central problem addressed by the `memory-context` module.

**RAG exists because context windows are finite.** If a context window could hold all knowledge relevant to any task at zero cost, there would be no need for retrieval. RAG is an engineering response to a fixed budget constraint: it selects which content to inject, not all content.

**`max_tokens` must always be set explicitly.** Without a cap, a model generating a long response can consume most of the remaining budget, leaving insufficient room for subsequent turns or forcing truncation of earlier history.

## 5. Implementation Connection

`labs/llm-fundamentals/lab-context-window` makes the limit concrete and observable. The lab:

- Measures the token cost of each prompt component individually (system prompt, user message, history)
- Progressively increases input size to approach the context limit and observes the API response
- Tests behavior when `input_tokens + max_tokens` exceeds the model's limit
- Demonstrates that truncated content produces no error — only a subtly degraded response

The lab uses the `light` infrastructure profile with a locally running Ollama model. Token counting uses `tiktoken` independently of the API call, so cost estimation can be tested without spending tokens.

## 6. Failure Modes and Limitations

**Silent truncation.** Most APIs truncate the oldest conversation turns when context overflows, without raising an error. The model generates a coherent-sounding response, but it has lost access to earlier instructions or context. The caller has no direct indication that truncation occurred unless they track token counts explicitly.

**Lost-in-the-middle degradation.** In long contexts, information placed in the middle sections receives systematically less attention than information at the start or end. For RAG and document analysis use cases, this means the position of retrieved chunks within the prompt affects retrieval fidelity — not just their presence.

**Runaway completion tokens.** A response with no `max_tokens` limit can grow to fill the remaining context budget. In a multi-turn application this leaves little space for subsequent turns, forcing earlier history to be truncated sooner than expected.

**Context window inflation.** Setting very large context windows "to be safe" increases per-call latency and cost proportionally. Context should be sized to the task, not maximized by default.

---

## 7. Summary

The context window is a fixed token budget shared by all input components and the model's output. Its limit exists because self-attention scales quadratically with sequence length. The engineering consequences are direct: truncation is silent, attention is not uniform across long contexts, input tokens are a recurring cost, and conversation state management falls entirely to the application layer. Every module that involves long inputs, multi-turn conversations, or retrieved content — RAG, memory, agents — is an engineering response to this constraint.
